# 单一当前 Profile 与整数顺序迁移

平台允许同时发布多个领域 Profile，例如通用、电商或金融 Profile。一个项目只能绑定一个领域 Profile，首版不支持 Profile 叠加、继承或规则合并。普通用户创建项目时不选择也不感知 Profile；AI PM 根据用户提交的项目目标、范围和领域信息，从当前可用 Profile 中自动匹配一个领域 Profile，版本始终使用该 Profile 的当前版本。普通用户界面、项目简报和人工校准点不展示 Profile 名称、版本或匹配置信度，用户只确认业务目标、范围和产物内容；Profile 绑定及版本仅供管理员在管理、迁移和故障诊断界面查看。每个领域 Profile 在平台运行时只保留一个当前可执行版本，并使用连续整数表示版本，例如当前 `version: 5`，历史项目通过 `1_to_2`、`2_to_3`、`3_to_4`、`4_to_5` 的不可跳跃迁移链升级。每次处理项目消息前先比较项目版本与所选 Profile 的当前版本，落后时取得项目级写锁并按顺序执行幂等、可 Dry Run 的迁移；项目及历史基线只记录当时的 Profile 标识、整数版本和内容哈希，完整发布内容由数据库中的不可变 Profile 版本记录提供，不为项目复制规则快照，旧 Profile 版本也不再运行。

平台必须内置一个不可停用的通用 Profile 作为兜底。AI PM 无法明确匹配任何专业领域 Profile 时自动绑定通用 Profile，不向普通用户暴露回退过程，也不能因匹配不明确而阻止项目创建。

项目在第一个人工校准点通过前，AI PM 可以根据新增信息静默更换所选领域 Profile；通过后仍允许更换，但必须完成影响分析并使项目进入 `REBASELINING`。切换不得尝试让旧 Profile 下的批准版本满足新 Profile，而应从受影响的最早阶段开始创建候选新版本，重新通过新 Profile 的门禁和必要人工校准，并以新基线显式取代旧基线。普通用户只感知需要重新确认的业务内容和影响，不暴露 Profile 切换这一内部实现原因。

迁移必须声明其影响类型。仅涉及结构转换、确定性重新渲染或按新规则重新校验的技术迁移可以自动完成；任何新增或改变业务语义、业务范围或业务选择的迁移，都必须暂停尚未处理的原始消息，将项目置为 `WAITING_FOR_HUMAN_ALIGNMENT`，由项目所有者确认后继续。

“批准产物不可变”只表示该历史版本不能被原地覆盖，不表示它永久保持当前有效。迁移影响批准产物时，项目进入 `REBASELINING`，旧阶段基线继续保留用于审计，但不再作为新 Profile 下的合规目标；系统以旧基线和迁移规则生成新候选版本，只对候选版本执行新 Profile 的校验、评审和必要人工确认。全部受影响阶段通过后封存新的阶段基线，并以显式 `supersedes` 关系取代旧基线。迁移流程不得要求已被取代的旧版本通过新规则，因此不会形成重复失败的校验循环。迁移成功或确认完成后，系统再恢复处理原始消息。

相邻版本迁移规则允许管理员直接修正，不再维护独立的迁移修订号或历史规则快照。每次迁移运行只记录当时规则的内容哈希。跨多个版本升级时，每个相邻版本步骤独立原子提交：某一步全部成功后立即更新项目版本，再执行下一步；后续步骤失败时项目停留在最后成功版本，下次仅从该失败步骤继续。只有项目到达所选 Profile 的当前版本后，原始消息才可进入 PM 或其他 Graph 节点。

迁移失败时项目仍停留在该步骤的来源版本，并在前端展示迁移失败，本次原始消息标记为 `FAILED_BEFORE_PROCESSING`，不得继续处理；管理员修复迁移并手动重试成功后，也不自动重放这条失败消息，用户需要主动点击重试或重新发送，避免产生重复业务操作。失败状态阻止项目对话、审批、变更及其他业务写入，但用户仍可查看和下载旧基线、项目历史及迁移错误报告。只要项目版本仍落后，后续每次用户对话都必须再次自动执行迁移，不因当前规则哈希与上次失败运行相同而跳过；管理员同时拥有手动重试入口。

如果迁移没有发生技术故障，只是新增或改变业务语义而进入 `WAITING_FOR_HUMAN_ALIGNMENT`，原始消息继续保持待处理；项目所有者完成确认、迁移成功后，系统自动恢复这条原始消息。并发请求由项目级写锁串行化，避免同一迁移被同时执行。已经成功升级到目标版本的项目不因迁移规则后来改变而重复执行旧迁移；若成功结果后来被证明需要业务或结构修正，应通过下一个 Profile 版本或项目变更重新基线化。
