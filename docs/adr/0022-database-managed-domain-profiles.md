# 数据库管理领域 Profile

PostgreSQL 是领域 Profile 的唯一权威来源和版本库，Profile 定义、组成内容、草稿、发布记录、当前版本指针、迁移声明、发布校验结果和运行快照均保存在数据库中，不提交到 GitLab。GitLab 继续只保存项目的批准产物和阶段基线。

首版只有系统角色 `ADMIN` 可以创建、编辑、发布和停用 Profile，修改迁移规则以及手动重试失败迁移；普通用户不进入 Profile 管理界面。Profile 发布不要求编辑人与审批人分离，ADMIN 可以直接发布自己的草稿，但系统必须记录发布人、发布时间、内容差异和静态检查结果。系统内置的通用 Profile 不得停用或删除。

专业 Profile 停用只禁止 AI PM 为新项目绑定，不影响已经绑定的项目继续使用该 Profile 和执行后续版本迁移。系统不得因停用而把已有项目静默切换到通用或其他 Profile；管理员需要更换已有项目的 Profile 时，必须单独触发影响分析和重新基线化。已绑定项目遇到 Profile 缺陷时应发布新版本修复，而不是通过停用阻断全部项目。

每个专业 Profile 必须定义结构化的适用条件和排除条件。AI PM 基于项目目标、范围和领域事实判断是否明确满足适用条件且不命中排除条件；满足时绑定该专业 Profile，否则使用系统内置的通用 Profile。首版不引入关键词权重、综合评分或置信度阈值。

每个领域 Profile 以稳定的 `profile_id` 标识，并通过连续整数 `version` 管理发布版本；同一 Profile 同时只能有一个当前可执行版本。编辑在草稿记录中进行，发布时执行结构校验、相邻迁移存在性检查和规则引用检查，全部通过后在事务中生成不可变发布快照并原子更新当前版本指针。项目运行绑定明确的 `profile_id`、整数版本和内容哈希，禁止直接读取仍在编辑的草稿。

ADMIN 准备发布下一版本时，平台比较当前发布快照与草稿，自动生成相邻版本迁移草稿，为新增字段、产物、校验、评审和渲染变化建议对应迁移动作。ADMIN 必须检查、修改并明确确认迁移草稿，平台和 AI 均不得自行发布；静态发布检查要求每项有影响的 Profile 差异都声明处理方式，随后迁移定义与新 Profile 版本在同一发布事务中生效。

Profile 新版本发布成功后立即成为当前版本，首版不提供定时、灰度或按项目白名单发布。已经开始执行的 Graph Run 固定使用启动时记录的 Profile 发布快照，不在运行中切换，也不因新版本发布而中断；后续新 Run 才使用当前版本，新 Run 所属项目版本落后时先完成相邻版本迁移。

Profile 当前版本指针只允许单向递增，不支持将历史版本重新设为当前版本。相邻版本迁移规则错误时由 ADMIN 直接修正规则并让失败项目重试；已经发布的 Profile 内容本身存在错误时必须发布下一个整数版本向前修复。历史 Profile 发布快照始终只用于审计和影响追查，不参与运行时回退。

Profile 采用单一 JSONB 聚合存储，不将术语、能力、产物规则和质量门禁拆成大量独立业务表。`domain_profile` 保存稳定身份、名称、状态和当前版本；`domain_profile_draft` 保存可编辑的完整 `content` JSONB 与乐观锁版本；`domain_profile_version` 保存不可变的完整 `content` JSONB、整数版本和内容哈希；`profile_migration` 保存相邻版本的迁移定义 JSONB 与当前内容哈希。管理界面可以按适用范围、术语、能力、产物规范、校验、评审、Prompt 上下文、追踪、质量门禁和渲染规则分区编辑，但发布和审计始终以完整 Profile 聚合为单位。

Profile 中的 `prompt_context` 仅提供领域术语、常见流程、必须关注的问题、领域风险、产物内容指导和评审关注点。AI PM 可以用这些知识识别缺口和提出问题，但不得把领域惯例直接写成未经项目确认的业务事实。系统角色、Graph 阶段和状态流转、权限与安全策略、人工校准规则、工具调用能力及平台统一输出协议不属于 Profile，由平台系统 Prompt 和运行时代码统一维护，Profile 内容不得覆盖。

Profile 的质量规则分为两类并独立执行。`validation_rules` 只能使用平台白名单中的确定性规则类型，由程序检查必填、唯一性、枚举、引用、状态和覆盖关系，相同输入必须产生相同结果；`review_rules` 定义完整性、合理性、歧义、可实现性和可测试性等语义评审标准，由 Reviewer Agent 执行并要求引用具体产物证据。阶段质量门禁必须同时满足两类规则；语义评审发现缺少项目业务决策时，转入人工校准而不是由 Reviewer 或 Author 自行补充。

平台统一维护各类产物不可删除、不可重命名的基础 Schema，确保 Graph、追踪关系和下游阶段始终消费稳定结构。Profile 可以将基础字段设为必填、增加字段约束和校验、在统一的 `domain_extensions` 容器中定义领域专属结构，并增加对应渲染章节；Profile 不得覆盖或移除基础字段。产物运行时 Schema 由平台基础 Schema 与当前 Profile 的领域扩展确定性合成。

专业 Profile 不要求覆盖所有交付阶段，只维护确实存在领域差异的阶段扩展。某阶段未配置领域扩展时继续执行平台基础 Schema、系统 Prompt 和基础质量规则，不继承通用 Profile 的内容，也不跳过该阶段。通用 Profile 是自动匹配的兜底领域知识包，而不是其他 Profile 的父版本。

发布新版本时不扫描、不校验也不升级任何真实项目。发布校验只执行 Profile 结构、相邻版本迁移存在性、允许操作类型和规则引用等静态检查；真实项目仅在下一次收到消息时使用自身数据按需迁移和校验。Profile 发布成本因此不随历史项目数量增长，也不建设独立的迁移测试样本库。

历史发布快照不再作为可选择或可执行版本，但作为永久审计记录保留，用于项目基线审计、升级影响分析和故障追查。历史发布快照不得修改；被任何项目、产物或基线引用的版本禁止删除，新项目和 PM 也不能主动选择历史版本。Profile 版本发布后如需修正内容，必须产生下一个整数版本。
