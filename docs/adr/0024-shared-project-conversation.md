# 每个项目使用一条共享对话时间线

每个项目只有一条共享对话时间线，V2 使用 `project_message` 保存直接关联 `project_id` 的项目消息，废弃 V1 的 `conversation_message`，不建立额外 Conversation 或 Thread 表，也不支持项目内私聊。项目所有者和项目成员查看相同的用户消息、助手回复、过程时间线和可见产物变化；查看者只能读取。所有业务输入因此进入同一个 AI PM 上下文和项目单写者流程，避免不同成员分别与 PM 对话后形成互相冲突的项目真相。

共享可见不等于多人同时发言。平台沿用现有项目占用逻辑：Redis 以项目 ID 保存当前临时对话用户 ID，滑动 TTL 为 300 秒；项目没有占用者时，首个成功提交消息的 OWNER 或 MEMBER 取得对话权，同一用户后续每次成功提交 `DIRECT`、`STEER` 或 `QUEUE` 消息都将 TTL 重新延长到 300 秒。其他成员在 TTL 到期前只能查看，不能提交项目消息。页面浏览、接收助手输出和 SSE 心跳不续期；项目从当前 Run 开始，经过后续全部 `QUEUE` 消息，直到没有当前 Run 且公共队列清空为止，构成一个连续的对话处理期。服务端在整个自动处理期内定时续期当前对话用户的占用锁，使模型执行、阶段处理和排队等待均不会在中途被其他成员取得发言权。Run 进入 `WAITING_FOR_HUMAN` 时停止后台续期并恢复五分钟空闲竞争，当前用户每次成功提交与待确认事项相关的回答或补充时重新续期 300 秒；Run 恢复自动处理后再次持续续期。对话处理期结束后同样停止续期，并从停止续期时重新计算五分钟空闲时间。

对话占用锁只限制谁可以写入共享时间线，不决定业务批准权限，也不替代项目单写者、Delivery Run 或数据库行锁。Redis 丢失时占用权可以重新竞争，但不会造成两个 Graph 同时修改项目。取得、同用户续期和异用户拒绝必须通过单个 Redis 原子脚本完成，前端显示的占用者和剩余时间仅作提示，服务端提交检查为最终依据。

当前对话用户为 MEMBER，而 Run 进入只能由 OWNER 完成的人工校准点时，平台立即以原子操作释放该 MEMBER 的对话占用权，使 OWNER 可以直接取得发言权，不要求等待剩余五分钟。该释放只改变谁能向共享时间线提交消息，不取消或重建当前 Run，也不赋予 MEMBER 任何批准权限。

Run 等待 OWNER 校准期间，MEMBER 可以按共享对话规则取得发言权并补充意见，但其临时占用不能阻塞 OWNER。OWNER 提交“确认”或“驳回”属于治理操作，可以绕过 MEMBER 的占用检查；服务端在接受决议时原子地将发言权转交给该 OWNER、重置 300 秒 TTL，并从当前 Checkpoint 恢复 Run。

当前对话用户只能在对话处理期之外通过“结束对话/交接”操作主动释放发言权，使其他 OWNER 或 MEMBER 无需等待五分钟即可重新竞争。释放必须由服务端校验当前用户身份并通过 Redis 原子操作完成；关闭页面、断开连接或退出登录不自动释放，避免临时网络中断或误关闭导致发言权意外转移，仍以五分钟无新消息的滑动超时作为兜底。当前 Run 正在执行或仍有 `QUEUE` 消息等待时均不允许“结束对话/交接”，但当前对话用户可以选择“中断对话”来停止当前处理。

发言权交接不撤销或跳过已经提交成功的消息。原当前对话用户留下的 `QUEUE` 消息仍属于项目共享输入，继续保留在公共队列中，并与其他排队消息统一按照 `created_at` 顺序执行；交接只影响后续由谁提交消息。

尚未开始执行的 `QUEUE` 消息可以显式取消：消息提交者可以取消自己的待执行消息，项目 OWNER 可以取消项目内任意待执行消息。取消只将消息状态更新为 `CANCELLED` 并保留在共享时间线中用于审计，不物理删除；消息开始执行后不再适用排队消息取消操作，应通过运行中的 `STEER` 或后续 `QUEUE` 表达调整。

当前对话用户中断已经开始的处理时，不在 `project_message` 中引入 `CANCEL_REQUESTED`。对应助手消息在安全停止前保持 `RUNNING`，当前 `delivery_run.status` 临时变为 `STOPPING`；Worker 完成正在进行的原子区并在最近安全 Checkpoint 停止后，助手消息最终变为 `INTERRUPTED`，所有尚未执行的 `QUEUE` 消息统一变为 `CANCELLED`，不会继续启动下一 Run。若中断请求到达时全部处理已经完成，消息保持 `COMPLETED`。因此 `CANCELLED` 只表示消息从未开始执行，`INTERRUPTED` 只表示处理开始后被用户停止。

项目 OWNER 可以在 MEMBER 占用对话时绕过发言权限制发起强制中断，以停止失控、错误或高成本的项目处理。强制中断是治理操作而不是项目消息，不赋予 OWNER 在停止完成前提交业务输入或 `STEER` 的能力；Worker 仍按相同安全边界停止，且最终由 `stopped_by_user_id` 记录实际执行中断的 OWNER。安全停止完成时，平台将原 MEMBER 的对话占用权原子转交给发起中断的 OWNER，并将滑动 TTL 重置为 300 秒，使 OWNER 可以立即提交修正方向而无需再次竞争或等待超时。

`project_message` 使用固定字段 `stopped_by_user_id` 和 `stopped_at` 审计取消与中断：前者记录执行操作的用户，后者记录消息实际进入 `CANCELLED` 或 `INTERRUPTED` 的时间，具体语义由 `status` 区分。取消审计不新增原因 JSONB，也不建立独立取消记录表。

助手消息保存最终用户回复、状态、用户可见 `process` JSONB 和仅管理员可见 `diagnostics` JSONB；过程时间线只记录阶段、Agent、校验、发现、返工和决策摘要，不包含隐藏思维链。每个项目唯一当前 `delivery_run` 通过触发用户消息和响应助手消息关联这条共享时间线。

项目空闲时当前对话用户的消息以 `DIRECT` 模式启动新 Run。项目存在运行中 Run 时，只有当前对话用户可以明确选择 `STEER` 或 `QUEUE`：`STEER` 通过 `target_run_id` 关联当前 Run，在下一个安全 Checkpoint 边界由 AI PM 消费并调整当前计划；`QUEUE` 不关联当前 Run，等待当前 Run 进入终态后按消息创建时间启动下一 Run。`project_message` 自身的 `delivery_mode`、`target_run_id`、`status` 和 `created_at` 组成当前指引与待处理队列，不建立专用队列表。

`STEER` 不强行中断正在执行的模型调用或外部副作用。阶段进入 `SEALING`、Git Commit、基线 Tag 或数据库封存事务等不可打断区后，界面只允许 `QUEUE`；已经提交但尚未消费的指引如果错过安全边界，自动转换为排队消息，不能丢失。项目处于人工校准或失败恢复状态时仍遵守对应的受控输入规则。
