# AI 软件交付平台 V2 设计

## 1. 背景与目标

当前项目已经通过 LangGraph Multi-Agent 流程实现从需求输入到需求大纲、需求模块、PRD、架构、数据库、接口和测试用例的完整 Demo 链路，但现有流程以“Demo 优先：速度 > 细节”为主要约束，生成效果存在以下系统性问题：

- 大纲和需求模块粒度偏浅，无法直接支撑真实研发；
- 大纲、PRD、技术设计等阶段的职责互相侵入；
- Agent 会把未经用户确认的常见做法写入正式产物；
- 多 Agent 评审容易快速放行，缺少可核验的审核证据；
- 用户的问答、澄清、范围限定和流程指令没有稳定的意图模型；
- 上游需求发生变化后，下游设计、代码和测试缺少精确的影响传播；
- 开发和测试尚未纳入同一条可追踪的软件交付链。

V2 的目标是把项目从“文档生成 Demo”演进为“AI 软件交付平台”：每个阶段只负责自己的专业产物，PM 对项目整体真相、决策和阶段推进负责，后续架构、开发和测试 Agent 遇到问题时优先向 PM 澄清，只有真正需要业务决策的事项才升级给人。

第一期聚焦需求业务效果，不同时实施完整的生产基础设施、自动开发和自动测试。

## 2. 已确认的设计决策

### 2.1 PM 自治边界

采用受约束自治：

- PM 可以处理实现细节、修复矛盾，并从已确认事实中推导结论；
- PM 可以自主采用低风险、可逆的工程默认值，并记录决策和依据；
- 涉及业务范围、优先级、成本、合规或不可逆选择时，必须升级给人；
- 系统运行失败、模型超时等属于技术故障，不伪装成业务问题要求人决策。

### 2.2 阶段推进

- PM 根据自动化质量门禁批准产物并推进阶段；其中结构、范围、版本和追踪由确定性规则校验，语义质量由专项 Reviewer 检查；
- 阶段推进不依赖用户反复回复“继续”；
- 只有存在人类决策项时才暂停流程；
- Agent 的自然语言判断不能直接改变项目阶段，状态转换由确定性策略代码执行。

### 2.3 基线与变更

- 批准产物成为不可变基线；
- 任何修改都创建新版本，不覆盖原版本；
- PM 对变更执行影响分析；
- 只有受影响的下游产物、任务、代码和测试会被标记为待更新；
- 基于旧基线执行的结果不能继续作为有效交付物。

### 2.4 事实治理

正式内容分为三类：

- 已确认事实：来自用户输入、上传材料或已批准产物；
- 可推导结论：由已确认事实推导，必须保留推导依据；
- 建议方案或假设：必须标记风险、适用范围和采用理由。

会改变业务行为的假设不能由 Agent 自动写入正式产物。

### 2.5 领域适配

产物采用“稳定核心 Schema + 可插拔领域 Profile”：

- 核心 Schema 保证跨阶段结构和追踪关系稳定；
- 领域 Profile 提供行业术语、典型场景、风险和质量检查项；
- PM 根据项目类型选择或组合 Profile；
- 不使用一套万能模板覆盖所有项目，也不允许完全自由生成。

### 2.6 对话中断

工作流采用“固定执行轨道 + 可中断对话”：

- 用户可以随时提问、澄清、修改范围、暂停或恢复；
- PM 先识别意图、目标产物、作用范围和是否改变基线；
- 消息处理完成后恢复原任务；
- 被中断任务和恢复位置必须进入结构化状态。

## 3. 总体架构

采用契约驱动的阶段流水线，保留 LangGraph 作为执行引擎，但重新划分控制权：

```text
用户 / 下游 Agent
        |
        v
PM 控制面
  - 意图解析
  - 项目真相
  - 决策与 RFI
  - 版本与变更
  - 确定性调度
        |
        v
阶段执行模块
  - Context Projection
  - Stage Author
  - Deterministic Validators
  - Specialized Reviewers
  - Bounded Revision Loop
        |
        v
批准产物与追踪图
  - Requirements
  - Architecture / Design
  - Development Tasks / Code
  - Tests / Results
```

主 Graph 只负责控制和状态迁移；各阶段子图负责在明确契约内生成候选产物。Agent 不能直接修改共享项目状态，只能返回带基线版本的候选 Patch，由 PM 校验后提交。

## 4. PM 控制面

### 4.1 PM 的职责

PM 是项目控制面，负责：

- 维护项目目标、范围、事实、假设和决策；
- 理解用户和下游 Agent 的消息；
- 调度当前阶段任务；
- 处理澄清请求；
- 执行阶段质量门禁；
- 批准产物和推进阶段；
- 创建变更版本并传播影响；
- 只在需要人类业务决策时暂停。

PM 不越权替其他阶段生成专业产物。需求阶段可以由产品型 Stage Author 生成需求产物，架构、数据、接口、开发和测试分别由对应阶段执行模块负责。

### 4.2 PM 的深模块 interface

PM 每次处理消息只能产生以下结构化动作之一：

- `ANSWER`：回答问题，不改变基线；
- `APPLY_CLARIFICATION`：把用户回复应用到待确认事项；
- `CREATE_CHANGE`：创建变更请求，不覆盖原产物；
- `DISPATCH`：向阶段执行模块下达任务；
- `RESOLVE_RFI`：处理开发或测试提出的澄清；
- `ESCALATE`：请求人类做业务决策；
- `PAUSE`：暂停当前执行轨道；
- `RESUME`：恢复被中断任务。

动作必须携带：

- 意图类型和置信度；
- 目标阶段和目标产物；
- 允许与禁止修改的范围；
- 使用的事实、决策和基线版本；
- 是否改变已批准基线；
- 完成后恢复的任务位置。

### 4.3 意图模型

用户消息先转换为 `IntentEnvelope`：

```text
intent_type
target_stage
target_artifacts
include_scope
exclude_scope
referenced_versions
requested_effect
changes_baseline
confidence
resume_task
```

支持的主要意图包括：项目状态查询、待确认项回复、需求变更、范围限定、建议批准、暂停、恢复、失败重试、生成、重新生成和普通问答。

例如“只生成用户服务模块的测试用例”必须显式得到 `include_scope=[用户服务]` 和其他模块的排除范围，后续 Agent 无权扩大任务范围。

## 5. 项目真相模型

PM 不再把对话摘要当作项目事实源，而是维护以下结构化记录：

- `ProjectCharter`：项目目标、参与者、范围内、范围外、约束和成功指标；
- `FactRecord`：事实内容、类别、来源证据、状态和适用阶段；
- `DecisionRecord`：决策问题、选项、选择、理由、决策权限和影响范围；
- `OpenQuestion`：待确认问题、阻塞阶段、建议选项和是否需要人决策；
- `ArtifactManifest`：产物类型、版本、状态、输入版本、负责人和质量结果；
- `TraceLink`：事实、需求、设计、任务、代码和测试之间的关系；
- `WorkflowCursor`：当前阶段、当前任务、暂停原因和中断栈；
- `ChangeRequest`：变更原因、差异、影响集合和需要重新处理的下游内容；
- `RFI`：下游问题、上下文、答复和是否触发基线变更。

原始对话和上传材料作为证据库保留，但摘要无权修改项目真相。

## 6. 统一产物契约

### 6.1 产物信封

所有阶段产物使用统一外层结构：

```text
Artifact
  artifact_id
  type
  schema_version
  version
  status
  scope
  input_baselines
  facts_used
  decisions_used
  structured_content
  assumptions
  open_questions
  trace_links
  coverage_report
  validation_report
  provenance
```

Markdown、页面和导出文件只是 `structured_content` 的渲染结果，不是唯一事实源。

批准产物不可修改。旧 Markdown 导入 V2 时只能成为 `UNVERIFIED_DRAFT`，不能自动成为批准基线。

产物状态生命周期为：

```text
UNVERIFIED_DRAFT -> DRAFT -> VALIDATING
  -> REVISION_REQUIRED -> DRAFT
  -> BLOCKED
  -> APPROVED -> STALE -> SUPERSEDED
```

- `UNVERIFIED_DRAFT`：来源尚未验证的历史或导入内容；
- `DRAFT`：当前阶段生成的候选版本；
- `VALIDATING`：正在执行确定性校验和语义评审；
- `REVISION_REQUIRED`：存在可由当前阶段修复的问题；
- `BLOCKED`：存在人类决策项或缺失的必要上游输入；
- `APPROVED`：质量门禁通过的不可变基线；
- `STALE`：上游变化后仍可审计，但不能继续作为新任务基线；
- `SUPERSEDED`：已有替代它的新批准版本。

### 6.2 稳定追踪标识

- `GOAL-*`：项目目标；
- `ACTOR-*`：用户或外部参与者；
- `CAP-*`：业务能力；
- `SCN-*`：业务场景；
- `BR-*`：业务规则；
- `STATE-*`：状态和流转；
- `AC-*`：验收标准；
- `NFR-*`：非功能性要求；
- `DEC-*`：项目决策；
- `ADR-*`：架构决策；
- `API-*`：接口设计；
- `DATA-*`：数据设计；
- `TASK-*`：开发任务；
- `TEST-*`：测试用例。

追踪主链为：

```text
GOAL -> CAP -> SCN / BR -> AC / NFR
     -> ADR / API / DATA
     -> TASK -> CODE
     -> TEST -> RESULT
```

## 7. 阶段职责

| 阶段 | 负责产出 | 禁止内容 |
|---|---|---|
| 项目定义 | 目标、用户、范围、约束、成功指标 | 功能细节和技术方案 |
| 需求大纲 | 业务能力地图、主场景、术语、模块候选 | 字段、接口、数据库、部署 |
| 需求模块 | 场景、规则、状态、异常、验收标准 | HTTP、DDL、框架和代码方案 |
| PRD | 跨模块流程、全局规则、优先级、NFR | DDL、K8s、连接池和具体框架 |
| 架构设计 | 系统上下文、质量属性、ADR、部署关系 | 新增业务需求或修改验收标准 |
| 系统模块设计 | 模块职责、interface、依赖、数据所有权 | 越权修改 PRD |
| 数据库设计 | 实体映射、表、索引、迁移、一致性 | 新增无需求来源的业务字段 |
| 接口设计 | 契约、错误、幂等、分页、兼容 | 发明业务流程 |
| 开发计划 | 可执行任务、依赖、验收映射 | 用任务描述替代需求 |
| 代码实现 | 代码、迁移、配置和实现证据 | 静默修改需求或设计 |
| 测试设计 | 场景、数据、预期结果和需求覆盖 | 无证据宣称覆盖完整 |
| 测试执行 | 结果、缺陷、日志和验证证据 | 修改需求来让测试通过 |

## 8. 核心需求产物

### 8.1 需求大纲

大纲用于建立业务地图，必须包含：

- 业务背景和问题陈述；
- 项目目标及可衡量结果；
- 参与者和外部系统；
- 范围内和范围外；
- 核心场景和端到端主流程；
- 业务能力地图；
- 领域术语；
- 已确认约束；
- 假设和未决问题；
- 事实来源。

模块候选必须是业务能力，不能使用页面、微服务、公共模块或初始化模块代替业务领域。

大纲批准要求：事实覆盖率为 100%，每项能力能追溯到目标或场景，不包含技术设计，不存在高风险未确认假设，范围内外没有矛盾。

### 8.2 需求模块

需求模块用于形成可开发的业务规格，必须包含：

- 模块使命和业务价值；
- 参与者、前置条件和触发条件；
- 正常、备选和异常场景；
- 业务规则和业务数据语义；
- 状态和允许的状态转换；
- 权限和职责归属；
- 与其他业务能力的交互；
- 边界条件；
- Given/When/Then 验收标准；
- 分配到本模块的 NFR；
- 范围外内容、假设和未决问题。

每条业务规则至少由一个验收标准覆盖。跨模块职责必须有唯一所有者。需求模块不得包含 HTTP 路径、DDL、索引和框架选型。

### 8.3 PRD

PRD 负责统一已批准模块，形成研发可开工的需求基线，必须包含：

- 项目目标、范围和版本目标；
- 角色及权限模型；
- 端到端用户旅程和业务流程；
- 业务能力和模块关系；
- 跨模块规则及全局状态；
- 统一术语；
- 优先级和发布范围；
- 全局验收标准；
- 非功能性需求及适用场景；
- 数据保留、审计、隐私等业务要求；
- 外部系统职责和交互语义；
- 埋点和成功指标；
- 已批准决策、范围外、风险、假设和未决问题；
- 完整需求追踪矩阵。

PRD 不包含 DDL、HTTP 请求响应、K8s YAML、连接池数量、具体框架和无依据的人天估算。

PRD 批准意味着架构阶段可以开始，开发和测试能够理解全部业务行为，但实现方式仍由后续阶段决定。

## 9. Graph 编排与 Agent 分工

### 9.1 主 Graph

```text
接收消息
  -> 意图解析
  -> PM 策略决策
     -> 回答
     -> 应用澄清
     -> 创建变更
     -> 请求人决策
     -> 调度阶段任务
  -> 阶段子图
  -> 自动质量门禁
     -> 返工
     -> 阻塞
     -> 批准并推进
```

### 9.2 阶段子图

所有阶段复用统一执行骨架：

```text
准备 Context Projection
  -> 生成结构化草稿
  -> 确定性校验
  -> 独立质量评审
  -> 问题归并
  -> 定向修正
  -> 重新校验
  -> 返回 StageResult
```

生成 Agent 不能批准自己的产物。Reviewer 不与生成 Agent 自由聊天，只返回结构化问题。返工应定位到字段、规则或章节，禁止无原因整篇重写。评审循环有固定上限，重复失败时输出诊断结果而不是无限循环。

阶段子图只返回 `StageResult`，不直接推进项目：

```text
StageResult
  candidate_artifact
  baseline_versions
  proposed_patch
  validation_report
  review_findings
  coverage_report
  assumptions
  open_questions
  provenance
```

PM 校验基线版本、Patch 范围和门禁结果后，才可以批准产物并更新 `WorkflowCursor`。如果基线已经变化，`StageResult` 失效并重新调度，不能尝试把旧结果合并进新基线。

### 9.3 按验证能力分工

- `StageAuthor`：按阶段契约生成候选产物；
- `CompletenessReviewer`：检查遗漏和覆盖；
- `ConsistencyReviewer`：检查事实、术语、状态和跨产物矛盾；
- `ScopeReviewer`：检查越权和范围漂移；
- `FeasibilityReviewer`：在技术阶段检查可实现性；
- `TestabilityReviewer`：检查需求和验收标准是否可验证；
- `TraceabilityReviewer`：检查追踪关系；
- `DomainProfileReviewer`：执行领域特有规则。

PM 按阶段选择必要 Reviewer，不使用固定的多人格讨论代替质量规则。

### 9.4 Context Projection

Agent 只接收当前任务需要的上下文：

- 当前批准基线；
- 相关事实和决策；
- 允许修改范围和禁止变更项；
- 领域 Profile；
- 未解决问题；
- 直接上游产物；
- 当前验收规则。

完整聊天记录作为证据保留，不默认注入所有 Agent。

## 10. 质量门禁

阶段批准依次检查：

1. Schema 有效；
2. Profile 必填内容完整；
3. 每项结论具有事实、决策或上游来源；
4. 没有当前阶段禁止的内容；
5. 没有遗漏上游要求；
6. 没有跨事实或跨产物矛盾；
7. 验收标准可验证；
8. 不存在待人决策项；
9. Reviewer 提供了具体检查证据。

硬门禁为：

- 事实覆盖率 100%；
- 需求追踪完整率 100%；
- 阻塞级矛盾 0；
- 阶段越权内容 0；
- 未确认业务假设 0；
- 无验收标准的业务规则 0；
- 无所有者的跨模块职责 0；
- Profile 必填项遗漏 0。

不使用不可解释的单一综合分数决定是否通过。

“事实覆盖率 100%”表示与当前产物范围相关的每条已确认事实都必须被使用，或者以明确理由标记为不适用于该产物；它不要求把无关事实复制进每份文档。

## 11. RFI 澄清协议

开发、测试和其他下游 Agent 发现歧义时提交：

```text
RFI
  question
  asker
  task_id
  baseline_versions
  affected_requirement_ids
  category
  blocking
  evidence
  options
  recommendation
```

PM 只能使用以下处理结果：

- `ANSWER_FROM_BASELINE`：从批准事实或产物回答；
- `PM_DECISION`：采用低风险、可逆的工程默认值；
- `CREATE_CHANGE_REQUEST`：暴露上游需求或设计缺陷；
- `HUMAN_ESCALATION`：需要人类业务决策；
- `REJECT_OUT_OF_SCOPE`：问题超出当前任务范围。

所有答复进入决策记录，并通知受影响任务，确保不同 Agent 获得一致答案。

## 12. 变更与状态安全

上游变更流程为：

1. PM 创建 `ChangeRequest`；
2. 创建新的上游产物版本；
3. 根据 `TraceLink` 计算影响集合；
4. 仅将受影响的下游产物标记为 `STALE`；
5. 各阶段基于新基线增量处理；
6. 验证后形成新的端到端一致版本。

多个 Reviewer 可以并行读取同一版本，但 Agent 不能直接修改中心状态。候选 Patch 提交时执行乐观版本检查；基线已变化则旧结果失效。每个节点支持幂等重试和 checkpoint。

## 13. 架构、开发与测试闭环

### 13.1 架构和详细设计

架构阶段消费批准 PRD，输出系统上下文、质量属性场景、ADR、模块和部署关系、数据所有权、风险及验证方案，并建立 `NFR -> ADR` 追踪。

系统模块、数据库和接口产物分别负责自己的设计。任何新增字段、接口或模块都必须引用需求和 ADR。技术阶段发现业务缺口时提交 RFI，不能自行增加业务需求。

### 13.2 开发计划和实现

开发任务包含：目标、输入版本、允许修改范围、需求和设计引用、前置任务、预期代码区域、测试要求、完成证据和非目标。

开发 Agent 每次只执行一个批准任务。实现结果必须包含修改文件、实现的需求和设计 ID、测试证据、偏离设计项、风险、未完成项和提交标识。开发 Agent 无权为了实现方便修改验收标准。

### 13.3 测试设计和执行

测试从验收标准和技术设计生成，覆盖业务场景、规则、状态、接口、集成、数据一致性、性能、安全和回归。每个测试必须追踪到需求和目标接口或模块。

测试失败由 PM 分类：

- `IMPLEMENTATION_DEFECT`：返回开发修复；
- `DESIGN_DEFECT`：创建技术设计变更；
- `REQUIREMENT_GAP`：创建需求新版本；
- `TEST_DEFECT`：修正测试；
- `ENVIRONMENT_FAILURE`：恢复执行环境；
- `BUSINESS_DECISION_REQUIRED`：升级给人。

只有最后一类需要人类决策。

### 13.4 完成交付条件

- 计划内需求均有批准版本；
- 需求均有对应设计和任务；
- 任务均有实现证据；
- 验收标准均有测试；
- 必须执行的测试均通过；
- 没有阻塞 RFI 或未决业务决策；
- 没有仍被视为有效的旧基线任务或产物；
- PM 已生成完整发布追踪报告。

## 14. 质量评测体系

### 14.1 黄金项目集

建立包含用户中台、电商交易、内部审批、开放平台和数据处理等类型的黄金项目集。每个项目保存原始材料、多轮对话、已确认事实和决策、必须包含和禁止包含的需求、参考产物、预期阶段转换和升级决策。

线上“用户中心”对话作为第一条回归样例。

### 14.2 四层评测

1. 确定性校验：Schema、必填项、ID、追踪、范围、版本和禁止内容；
2. 语义评测：忠实度、完整性、一致性、场景深度、可测试性和领域符合度；
3. 缺陷注入：删除场景、篡改规则、引入假设、混入下阶段内容、制造矛盾、使用过期基线；
4. 端到端执行：验证架构、开发和测试能否消费产物，并在歧义时正确发起 RFI。

### 14.3 关键指标

- 已确认事实覆盖率；
- 无依据内容比例；
- 需求遗漏率；
- 跨产物矛盾率；
- 阶段越权率；
- 需求追踪完整率；
- 验收标准可测试率；
- Reviewer 缺陷召回率和误报率；
- 意图分类准确率；
- 人类决策升级准确率；
- RFI 一次解决率；
- 变更影响分析准确率；
- 下游返工次数；
- 从需求到测试通过的整体成功率。

评测结合确定性规则、专项 Reviewer、人工抽样和黄金参考答案。LLM Judge 只能作为信号之一，不能单独批准产物。

### 14.4 可复现性

每次运行记录模型参数、Prompt/Profile/Schema 版本、输入产物哈希、工具调用、结构化输出、Validator 和 Reviewer 结果、重试过程、token、耗时、成本和最终批准依据。

任何模型、Prompt、Profile、Schema 或 Graph 改动都必须跑完整黄金项目集并与当前基线比较，检查退化后才能发布。

## 15. 渐进迁移

### 15.1 阶段 0：效果基线

- 整理“用户中心”黄金样例；
- 补充意图中断、范围限定和需求变更回归；
- 保存 V1 产物作为对照；
- 建立 Validator 和评测报告；
- 量化现有事实遗漏、无依据内容、越权和矛盾。

### 15.2 阶段 1：需求流程 V2

第一期实现：

- PM 控制面和 `IntentEnvelope`；
- 项目真相模型；
- 事实、决策、假设和未决问题；
- 产物信封和不可变版本；
- 大纲、需求模块和 PRD Schema；
- 核心 Validator 和需求 Reviewer；
- 结构化 RFI；
- 基础领域 Profile；
- Markdown 渲染；
- 用户中心黄金项目回归。

第一期不包含架构 V2、代码生成、自动开发、自动测试执行、大规模基础设施重构和前端整体重写。

### 15.3 阶段 2：双轨运行

V1 和 V2 对同一输入生成对比报告。V2 初期使用影子模式；达到门禁后新项目默认 V2，旧项目保留 V1 或选择导入。通过功能开关支持回退。

### 15.4 阶段 3：架构与详细设计 V2

接入架构、ADR、系统模块、数据库、接口、技术 RFI 和设计变更影响分析。

### 15.5 阶段 4：AI 开发

接入开发计划、任务隔离、测试驱动实现、代码审查、CI 证据、开发 RFI 和 `TASK -> CODE` 追踪。

### 15.6 阶段 5：AI 测试与发布

接入测试计划、执行、缺陷回流、性能和安全测试、发布门禁及端到端追踪报告。

## 16. 第一期验收标准

以“用户中心”黄金项目为例：

- 用户明确排除的 Token、会话和锁定能力不会重新出现；
- 未确认的密码重置、短信、API Key 网关等不会进入正式需求；
- 大纲不包含页面、数据库、接口和部署设计；
- 需求模块覆盖正常、备选、异常、边界、状态和验收标准；
- PRD 不包含 DDL、HTTP 契约和 K8s YAML；
- 所有事实和需求具有稳定追踪 ID；
- 所有业务规则具有验收标准；
- “继续”“只生成某模块”“是否更新”等回归对话不会错误推进或扩大范围；
- 注入的阻塞缺陷能够被 Reviewer 定位并给出证据；
- V2 输出通过人工产品评审，并能作为后续架构阶段输入；
- V1 可继续运行，V2 发生严重回归时能够通过功能开关停用。

## 17. 非目标

本设计不要求第一期完成：

- 认证、租户、计费和完整生产基础设施；
- 所有领域 Profile；
- 全自动架构、开发、测试和发布；
- 大规模替换当前数据库和前端；
- 让 LLM 自主决定不可逆业务事项；
- 一次性迁移所有历史项目为批准基线。

## 18. 设计原则总结

- 项目真相优先于聊天摘要；
- 结构化契约优先于自由 Markdown；
- 阶段职责优先于万能 Agent；
- 确定性状态转换优先于 LLM 自由路由；
- 证据化质量门禁优先于“审核通过”式评价；
- 不可变基线和影响传播优先于静默覆盖；
- PM 受约束自治，只有真正的业务决策升级给人；
- 先把需求流程做深、做准，再逐步接入架构、开发和测试。
